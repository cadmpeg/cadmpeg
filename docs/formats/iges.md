Record offsets, field widths, and endianness are also maintained as a machine-checked table in [`docs/layouts/iges.md`](../layouts/iges.md), generated from `docs/layouts/iges.toml`. That table is the canonical source for the numbers; the prose below carries the semantics. `cargo test -p cadmpeg --test layout_tables` proves the two agree.

## Physical representation

The representation flag is in the first 80 bytes. A `C` in byte 73 identifies Compressed ASCII. The other bytes of its flag record are printable ASCII. An `S` in byte 73 identifies Fixed ASCII.

The Binary representation starts with one 80-byte Binary Flag Section. Byte 1 is ASCII `B`. Bytes 2 through 5 are the big-endian unsigned 32-bit value `75`, which is the count of the remaining flag bytes. Bytes 6 through 11 are the one-byte bit lengths `Is`, `Id`, `NXs`, `NFs`, `NXd`, and `NFd`. Bytes 12, 17, 22, 27, 32, and 37 are ASCII `B`, `S`, `G`, `D`, `P`, and `T`. Each letter is followed by a big-endian unsigned 32-bit displacement for that section. Bytes 42 through 72 are unassigned. Byte 73 is ASCII `B`, bytes 74 through 79 are ASCII blanks or zeroes, and byte 80 is ASCII `1`. Detection reads the identifier, the remaining-byte count, the six section letters, byte 73, the blank-or-zero padding, and byte 80. It constrains no other byte, and it does not require the record to be printable ASCII, because the count field and the six bit lengths are binary values.

The Fixed ASCII representation is an ordered sequence of physical lines. A canonical line contains an 80-byte card followed by a line ending. A conformant line has exactly 80 payload bytes; the final line may end at file end. Card bytes 1 through 72 are section data. Byte 73 is the section marker. Bytes 74 through 80 are the right-aligned decimal sequence field. Parameter Data cards instead use bytes 65 through 72 for the right-aligned Directory Entry back-pointer, byte 73 for the `P` marker, and bytes 74 through 80 for the Parameter Data sequence. A canonical physical line before the Terminate card is one 80-byte card with a recognized section marker and a valid positive sequence. A short, blank, or other unmarked line before Terminate is malformed and is not an opaque record. A recognized section marker with an absent, unreadable, or disagreeing sequence is recoverable, and a line before Terminate that carries more than one 80-column card is recoverable under stated conditions; the record quarantine section states both recoveries and the framing loss they charge. Any other physical line with more than 80 payload bytes before Terminate is malformed, and bytes beyond column 80 do not form another card. The Terminate card is the last sequenced line, so bytes after its 80-byte card and before the next line boundary are not an unsequenced line and are malformed. Unsequenced lines may follow the Terminate line and are ignored by conforming postprocessors. The decoder has a CADIR recovery for a same-line suffix: when the first 80 bytes are a valid Terminate card, it retains the card and the suffix as a separate opaque `post-terminate` physical record, with no section or sequence semantics assigned to the suffix. This follows the fixed-line and post-Terminate rules in [IGES 5.3 §2.2](https://paulbourke.net/dataformats/iges/IGES.pdf) and [§2.2.4.6](https://paulbourke.net/dataformats/iges/IGES.pdf).

Byte positions are one-based in this specification. Source spans use zero-based half-open byte ranges. Parsing records the card payload and line ending as disjoint source spans before interpreting fields. A short card, a noncanonical line ending, and bytes after the Terminate card remain separate physical records with their original spans.

The canonical section order is Start (`S`), Global (`G`), Directory Entry (`D`), Parameter Data (`P`), and Terminate (`T`). Section sequences are positive decimal integers starting at one and increasing by one within each section. A Directory Entry occupies two consecutive `D` cards. Its first card has an odd sequence and its second card has the following even sequence. Directory pointers refer to the odd Directory Entry sequence. Zero is a null pointer where the owning field permits null.

The Terminate data area contains four eight-byte fields: `S` plus the seven-digit Start count, `G` plus the seven-digit Global count, `D` plus the seven-digit Directory Entry card count, and `P` plus the seven-digit Parameter Data card count. The remaining data area is blank.

## Global section

The twenty-six-field table and disposition matrix below state the IGES 5.1–5.3 Global profile. A file declaring version flag `6` or `8` uses its own profile before any later-profile default or field is considered.

The IGES 4.0 Global profile has twenty-four fields. It has no fields 25 or 26, accepts only the two-digit year form `YYMMDD.HHNNSS` for field 18, and supplies field-specific defaults only for fields 1, 2, and 23. Empty numeric and string fields otherwise take their data-type implicit defaults. The V4.0 profile therefore uses zero significant digits when fields 9 or 11 are empty, zero minimum resolution when field 19 is empty, no line-weight scale when field 17 is empty, and no scale or units flag when fields 13 or 14 are empty. A record with more than twenty-four Global fields is retained with `iges/global.noncanonical-framing`; fields after 24 are ignored. These rules are defined by [IGES 4.0 §2.2.4.2](https://www.govinfo.gov/content/pkg/GOVPUB-C13-7b81ba8b0f709555f162cb496aa63b3b/pdf/GOVPUB-C13-7b81ba8b0f709555f162cb496aa63b3b.pdf).

The IGES 5.0 Global profile has twenty-five fields. It accepts the two-digit year form `YYMMDD.HHNNSS` for field 18 and includes field 25 as the model date; field 26 is not present. Empty field 13 uses model scale `1.0`, while empty field 14 has no units-flag default and therefore leaves the millimetre length factor unresolved. Field 16 defaults to `1`; when field 16 is omitted, field 17 may also be omitted and no line-weight scale is defined. When field 16 is present, field 17 is required: a positive value defines the uniform physical-width series, while `0` selects relative Directory line-weight numbers. A relative number remains in `line_weight_number` and has no `line_weight_mm` value. The V5.0 profile uses the 5.0 field count and does not resolve field 26 as application-protocol metadata. These Global rules are defined by the [IGES 5.0 Recommended Practices Guide](https://nvlpubs.nist.gov/nistpubs/Legacy/IR/nistir4600.pdf), while the complete 5.0 comparison remains tracked in `GL-12`.

The Global field categories and empty-field defaulting rule follow [IGES 5.3 §2.2.1](https://paulbourke.net/dataformats/iges/IGES.pdf). The Global data-type rules follow [§2.2.2](https://paulbourke.net/dataformats/iges/IGES.pdf). The field definitions and default values are in [§§2.2.4.3.1–2.2.4.3.26](https://paulbourke.net/dataformats/iges/IGES.pdf).

The Global data stream is the concatenation of bytes 1 through 72 from its cards. Its first value defines the parameter delimiter and its second value defines the record delimiter. Each is a one-character Hollerith string. Omitted first and second values select comma and semicolon respectively.

A Hollerith value is an unsigned decimal byte count, the byte `H` or `h`, and exactly that many following bytes. Delimiters inside the counted payload are data. The count and `H` header must be on one Global card; the counted payload may cross card boundaries. Integer values are signed decimal integers. Real values accept a decimal point and an exponent introduced by `E`, `e`, `D`, or `d`. An empty or blank-only field between delimiters is omitted. The record delimiter terminates the Global record. A non-string Global value and its following delimiter must be on one card. A split numeric value is malformed but does not change the Global field boundaries; the field resolver applies that field's fallback and reports its field loss.

An IGES real is a sending-system approximation. A `D` or `d` exponent selects the Global double-precision significance; every other real spelling selects the Global single-precision significance. For a nonzero real value `x` with `p` declared significant digits, its representation uncertainty is `0.5 × 10^(floor(log10(abs(x))) - p + 1)`. Zero and integer tokens have zero representation uncertainty. Two redundant numeric fields agree when their absolute difference is no greater than the sum of their representation uncertainties.

For the IGES 5.1–5.3 profile, Global fields are ordered as the twenty-six fields in Table 1. Fields 1 and 2 are required-default delimiter fields. Fields 3 through 11 and 17 through 19 are required-no-default fields. Fields 12 through 16 and 20 through 26 are required-default fields. The defaults are: field 1 comma; field 2 semicolon; field 12 the value of field 3; field 13 `1.0`; field 14 inches (`1`); field 15 the name for the default inches selection; field 16 `1`; field 20 `0.0`, which means that the maximum coordinate is unspecified; fields 21 and 22 NULL; field 23 `3`; field 24 `0`; and fields 25 and 26 NULL. Field 15 is ignored when it is inconsistent with field 14 unless field 14 is `3`. Table 1 assigns each field the String, Integer, or Real data type. Every field also has a data-type implicit default: zero for an Integer field, zero for a Real field, and NULL for a String field. When the file omits or blanks a field, the field-specific default applies, or the data-type implicit default applies when the field has no field-specific default. Either assignment is silent. The disposition matrix below names the three fields whose implicit default the decoder replaces, and each replacement reports a loss. A supplied value must have its declared lexical type, valid numeric or date syntax, a payload that satisfies [IGES 5.3 §2.2.2.3](https://paulbourke.net/dataformats/iges/IGES.pdf), and a value inside the range its own field section states. Malformed supplied data never selects a default. It selects the matrix fallback and reports the matrix loss. Only a defect that leaves a field boundary unknown refuses the file: the field 1 and field 2 delimiter declarations, because those declarations frame every later field in every section; a prohibited delimiter byte, because it is ambiguous in Parameter Data; an unreadable or over-long Hollerith byte count; a Global section with no fields; and a record that never reaches its record delimiter. Every other Global defect resolves to a matrix fallback. Field 19 defines the smallest discernible model-space distance under [IGES 5.3 §2.2.4.3.19](https://paulbourke.net/dataformats/iges/IGES.pdf). A supplied zero is retained as zero and makes field-19 distance comparisons exact. Face-local carrier agreement uses this declared value; face-local sewing also applies the coordinate-quantum rule stated in the face topology section. Other consumers apply the separate computational floors stated below. Field 18 and a supplied field 25 use `15HYYYYMMDD.HHNNSS` or `13HYYMMDD.HHNNSS`, with the ranges stated by the format. The declared field-23 value is recorded verbatim as the `iges_version_flag` source attribute, including a value the format does not define. A version flag below `1` is assigned `3` and a version flag above `11` is assigned `11`; that clamp is the effective postprocessor interpretation mandated by [IGES 5.3 §2.2.4.3.23](https://paulbourke.net/dataformats/iges/IGES.pdf), and the effective flag selects the version name recorded as the `iges_version` source attribute. Decode admits every declared version. The verified set is 5.1, 5.2, and 5.3. When the effective version is outside the verified set, or when the declared flag was clamped, the decoder reports `iges/source.dialect-unverified` and interprets the file with the semantics verified for 5.1, 5.2, and 5.3; the loss names the declared flag and the effective version. That loss is reported in both container-only and full decodes, and a container inspection reports it in the loss census stated under decode admission. The summary notes carry the effective version name as `iges_version`, and they carry the declared flag as `iges_version_flag` when the clamp changed it. Files declaring a version outside the verified set decode with that loss until their versions are verified against their own specifications.

### Global field disposition matrix

This matrix is the contract for Global field resolution. It states, for every field in Table 1, what the decoder produces when the file omits the field and what the decoder produces when the file supplies malformed data. The decoder separates two stages. The raw stage recovers field boundaries and nothing else. The resolved stage converts each raw field into a value, a fallback, or an absence, and charges the losses this matrix names.

A field is malformed when any of these conditions holds: the value has the wrong lexical type for its Table 1 data type; a numeric or date value has invalid syntax; a Hollerith payload contains a byte that [IGES 5.3 §2.2.2.3](https://paulbourke.net/dataformats/iges/IGES.pdf) forbids; or the value falls outside the range the field's own section states. A malformed field never selects its defined default.

Every field has a default, including a required-no-default field. [IGES 5.3 §2.2.2.1](https://paulbourke.net/dataformats/iges/IGES.pdf) sets the implicit default for an Integer field to zero, [§2.2.2.2](https://paulbourke.net/dataformats/iges/IGES.pdf) sets the implicit default for a Real field to zero, and [§2.2.2.3](https://paulbourke.net/dataformats/iges/IGES.pdf) sets the implicit default for a String field to NULL. [§2.2.3](https://paulbourke.net/dataformats/iges/IGES.pdf) directs the postprocessor to assign the explicit or implicit default to any empty field. The required-no-default class in §§2.2.4.3.3 to 2.2.4.3.11 and §§2.2.4.3.17 to 2.2.4.3.19 therefore means that the field has no field-specific default, not that an empty field has no value. An empty required-no-default field takes its data-type implicit default, and that assignment is silent.

The decoder departs from the implicit default for three fields, because for those three the implicit default is a value the field's own semantics cannot use. Fields 9 and 11 would take zero significant digits, which makes every real-token interval as large as the token itself and admits every numeric invariant. Field 17 would take a zero maximum line width, which makes the §2.2.4.4.12 thickness ratio zero for every entity. Each departure reports a loss, because the decoder supplies the value and the file does not.

Two Hollerith failures are distinct. An unreadable or over-long byte count leaves the payload boundary unknown, so it leaves every later field boundary unknown; that failure refuses the file. A forbidden byte inside a payload whose count is readable leaves every boundary known, so it makes one field unusable and charges that field's matrix loss.

For the IGES 5.1–5.3 profile, the decoder retains fields 1 through 26 and ignores any further field. Table 1 in [IGES 5.3 §2.2.4.3](https://paulbourke.net/dataformats/iges/IGES.pdf) lists twenty-six parameters and defines no continuation, so a longer record is recoverable but noncanonical. The V4.0 and V5.0 profiles apply their twenty-four- and twenty-five-field limits stated above.

Thirteen of the twenty-six fields have no production consumer: fields 5, 6, 7, 8, 10, 12, 18, 21, 22, 24, 25, and 26 have no accessor, and field 20 has a test-only accessor. Each of those fields takes the simplest disposition the rules allow.

Fields 13, 14, and 15 resolve at one decision point, because they produce one number. The IR stores lengths in millimetres only. When that point cannot produce a known millimetre factor, the decoder suppresses every geometry projection, retains the native records, and charges one `iges/global.length-unit-unresolved` loss. The decoder never guesses a unit factor and never guesses a model scale. The decision point tests the field 13 scale as well as the field 14 flag and the field 15 name, because the factor is the unit value divided by the scale. This loss is reported in both container-only and full decodes.

Field 15 carries one specification conflict. §2.2.4.3.15 gives field 15 the default name for the inches selection, and §2.2.4.3.14 delegates the unit to field 15 whenever field 14 is `3`. When field 14 is `3` and field 15 is empty, the first rule names inches and the second rule names whatever field 15 holds. The decoder does not resolve the conflict by taking the inches default, because a file that declares flag `3` states that its unit is not one of the enumerated units. The decoder reports an unresolved length unit instead.

The fields 9, 11, and 19 fallbacks are constants, never absences, because every consumer needs a number. Fields 9 and 11 use their constant on both the absent path and the malformed path. Field 19 uses the §2.2.2.2 implicit default on the absent path, and it uses the same value as a constant on the malformed path. The direction rule is that a fallback must not widen an admission the file did not justify. The direction follows from how each consumer uses the value.

Fields 9 and 11 set the representation uncertainty of a real token, which is `0.5 × 10^(floor(log10(abs(x))) - p + 1)` for `p` declared digits. The uncertainty falls as the digit count rises. A unit vector is admitted when its squared-norm interval contains `1.0`, an orthogonal pair is admitted when its dot-product interval contains `0.0`, and a transformation frame is admitted when each column interval contains `1.0` and the determinant interval contains its expected sign. A wider interval admits more in all three. A surface parameter range outside its neutral domain is snapped to the domain edge when its interval reaches that edge, so a wider interval admits more and also moves a value. An analytic surface normal sense matches the positive candidate before the negative one, so a wider interval admits more and resolves more ambiguity by test order. The face-sewing coordinate quantum is `10^(magnitude - p + 1)`, so a larger digit count welds fewer vertices. A smaller digit count therefore admits more in every monotone consumer, and the conservative direction is the larger digit count. The constant is `17`, which is the largest decimal significance any binary64 value carries and the largest significance this codec's own writer declares. No honest declaration exceeds it, so the fallback never widens an admission.

The spline weight comparison is the one non-monotone consumer of fields 9 and 11. Wider intervals make more weight sets compare equal, which admits more polynomial splines and rejects more rational splines. The digit count `17` is conservative for the polynomial direction and permissive for the rational direction, and no single constant is conservative for both.

Field 19 sets a coincidence distance. Composite curve joining, spline segment continuity, closed-path closure, arc radius agreement, swept profile closure, and conic endpoint agreement all admit more as the distance grows. A larger value therefore admits more, and the conservative direction is the smallest value. The constant is `0.0` millimetres. It is the §2.2.2.2 implicit default for an empty Real field, so the conservative direction and the specification agree here, and the decoder does not depart. §2.2.4.3.19 defines the field as a distance, so zero is its lower bound, and every consumer already defines its behavior at zero: the point comparison uses exact equality, the arc and plane gates raise it to their scale-relative computational floors, face sewing raises it to the coordinate quantum, and the writer replaces a non-positive neutral linear tolerance with its generated bound and reports `writer.minimum-resolution-adjusted`.

The plane classification and the spline closedness test are non-monotone consumers of field 19. Each compares a computed result against a declared flag, so a smaller distance admits more open and non-planar declarations and rejects more closed and planar ones. The constant `0.0` is conservative for the open and non-planar direction only.

A file that reaches the fields 9, 11, or 19 fallback charges more per-entity losses than a file that declares those fields, because the narrow constants reject borderline geometry. That cost is deliberate. Every rejection carries its own entity loss, so the report states what was dropped; a wider constant would instead admit geometry the file never justified and report nothing.

The reader ignores ASCII space padding outside counted Hollerith payloads when it reconstructs Global fields from fixed cards. Spaces inside a counted payload remain data. An omitted sender-product field is retained as NULL under [IGES 5.3 §2.2.2.3](https://paulbourke.net/dataformats/iges/IGES.pdf), with no loss. A malformed sender-product field is also retained as NULL and charges `iges/global.metadata-field-unusable`. Semantic writing always emits a valid sender-product field.
Semantic output uses one fixed Global profile. Fields 3 and 5 identify `cadmpeg`; field 4 is `generated.igs`; field 6 is `0.1`; fields 7 through 11 declare `32`, `38`, `6`, `308`, and `17`; field 12 is the empty receiver-product string; fields 13 through 17 declare model scale `1.0`, millimetres (`2`, `MM`), one line-weight gradation, and maximum line width `1.0`; fields 21 and 22 use the generated-file author marker `author` and organization `cadmpeg`; field 24 is `0`; and fields 25 and 26 are empty. Field 18 is the current UTC generation time. Field 19 is the larger of the neutral document's positive finite `tolerances.linear` and the generated geometry-resolution bound. Field 20 is the largest absolute coordinate in the emitted Type 110, Type 116, and Type 502 coordinate lists, or zero when those lists are absent. Field 23 is the selected target version flag. These values are output-profile metadata; they do not replace source metadata during decode. Semantic decode stores Global field 19 after conversion to neutral millimetres in `CadIr.tolerances.linear`; the neutral angular tolerance keeps its default. This is a CADIR decision. A decode with no supported millimetre factor retains the neutral linear default because it cannot convert the source value.

Semantic target profiles are explicit. IGES 5.1, 5.2, and 5.3 admit the complete emitted Type/form envelope: Types 100, 102, 104 Forms 0, 2, and 3, 110, 116, 123, 124, 126, 128, 141, 142, 143, 144, 186, 190, 192, 194, 196, 198, and Types 502, 504, 508, 510, and 514 Form 1. Generated Global field 19 is at least the shared neutral coincidence floor, every finite positive edge or vertex topology tolerance used by the writer, and the writer's scale-relative endpoint admission bound. The emitted field also uses the neutral document's positive finite `tolerances.linear` as a floor. When the geometry bound raises a positive source-declared tolerance, the writer emits `writer.minimum-resolution-adjusted` and names both values in the write report. The pcurve endpoint check and the generated field use the same effective topology tolerance.

Semantic output maps the neutral analytic surface family directly: Plane to Type 190 Form 1, circular cylinder to Type 192 Form 1, circular cone to Type 194 Form 1, sphere to Type 196 Form 1, and torus to Type 198 Form 1. A circular cylinder, circular cone, sphere, or torus must support B-rep topology and uses physically dependent Point Type 116 and Direction Type 123 entities. These analytic entities retain the exact unbounded carrier and its parameter frame without rational conversion. Types 192 through 198 are B-rep surface entities and are not emitted as standalone or trimmed-surface carriers. Type 108 and Type 120 do not express these analytic carriers, and Type 128 requires a finite parameterized patch. A non-B-rep analytic surface therefore refuses before bytes are produced. This refusal has no loss note because no output representation is selected.

Generated analytic frames accept normalized axis dot-product residuals through `1e-6`. The writer keeps the primary axis, removes its component from the reference axis, normalizes the repaired reference, and derives the third axis by a right-handed cross product. A placement's supplied third axis must have the same handedness and a cross-product residual through `1e-6`. Larger skew is malformed and is refused before output. The repair bound is a writer convention for finite-precision neutral frames, not an IGES file tolerance.

The format-authoritative numeric rules are Global real-token representation intervals, Global minimum resolution, the Global single-precision coordinate quantum, and the interval and domain invariants stated for each entity. Other numeric thresholds are codec policies. Decoder policies use machine-epsilon geometry classification, `10^-12` conic standard-position and NURBS-plane normal gates, scale-relative `10^-10` frame, carrier, endpoint, offset, spline, and conic-placement comparisons, and `2π × 10^-12` angular comparison. Writer policies use `1e-6` frame repair, `1e-10` NURBS closedness and same-value comparison, `1e-8` scale-relative endpoint admission, and the `1e-10` and `1e-12` scale-relative NURBS-plane construction gates. These policies accept or refuse a neutral projection or semantic write; they do not replace a Global tolerance, change an entity field, or claim authority as an IGES tolerance. Omitted parameter values use only the defaults stated by the corresponding entity definition, and malformed supplied values never select a default.

Global strings are unlimited-length Hollerith strings of printable ASCII bytes (`0x20` through `0x7E`). Blanks, parameter delimiters, and record delimiters are ordinary string data. ASCII controls (`0x00` through `0x1F` and `0x7F`) and bytes above `0x7F` are forbidden by [IGES 5.3 §2.2.2.3](https://paulbourke.net/dataformats/iges/IGES.pdf). A Global Hollerith payload containing either class is malformed. In fields 1 and 2 it refuses the file, because those fields frame the rest of the file. In fields 3 through 26 it makes one field unusable under the disposition matrix above, because the byte count still fixes the field boundary. The decoder retains the complete original byte image in source fidelity for every admitted file. Accepted sender-product and native-file-name strings become the corresponding source attributes.

Bytes 1 through 64 of Parameter Data cards form parameter fragments. Bytes 65 through 72 identify the owning odd Directory Entry sequence. Zero, an even sequence, and an absent Directory Entry sequence are invalid back-pointers. Fragments are grouped by that back-pointer and ordered by Parameter Data sequence. The Directory Entry Parameter Data start sequence and card count define the exact contiguous range. Every card in that range has the owning Directory Entry sequence, and no card outside the range has that owner. The count includes every owned card, including cards whose payload follows the record delimiter and contains comments. A disagreement is a defect in the file and not a refusal; the start pointer is the first Parameter Data sequence in [IGES 5.3 §2.2.4.4.2](https://paulbourke.net/dataformats/iges/IGES.pdf), the count is the number of lines in [§2.2.4.4.14](https://paulbourke.net/dataformats/iges/IGES.pdf), the card back-pointer is required by [§2.2.4.5.1](https://paulbourke.net/dataformats/iges/IGES.pdf), and comment lines remain in that count under [§2.2.4.5.3](https://paulbourke.net/dataformats/iges/IGES.pdf). The record quarantine section states the ownership order that resolves such a disagreement, the loss it charges, and when it quarantines the entity's Parameter Data instead. A record delimiter terminates the entity's primary parameters. The primary parameters are followed, before that delimiter, by zero or one associativity pointer group and zero or one property pointer group. Each present group starts with its count and then that many Directory Entry pointers. Comments begin after the record delimiter and are not entity parameters. The entity table supplies `NV`, the last specified or defaulted primary parameter index, before the groups defined by [IGES 5.3 §2.2.4.5.2](https://paulbourke.net/dataformats/iges/IGES.pdf). Type 123 Form 0 has X, Y, and Z at indexes 1 through 3 under [§4.20](https://paulbourke.net/dataformats/iges/IGES.pdf), so its groups begin at token index 4 after the entity type token. A Hollerith header (its count and `H`) must be on one Parameter Data card, but its counted payload may cross cards. A numeric field and its following delimiter must be on one Parameter Data card. A split Hollerith header or numeric field is a defect in that entity's Parameter Data; the decoder quarantines that record and retains its raw cards. The decoder uses a proven entity-table boundary before generic recovery. For an entity form without a usable registered primary layout, the CADIR recovery rule selects a suffix only when exactly one structurally closed candidate is fully target-valid. If no candidate or more than one candidate is target-valid, the decoder does not infer a boundary: it retains the complete token sequence as primary parameters and creates no association or property links. On a required back-pointer route, a structurally closed suffix whose pointers do not resolve remains visible as an invalid group; if no target-valid boundary exists and multiple structural candidates remain, the boundary is not guessed. A required back-pointer route with an ambiguous or invalid group emits a finding while retaining all raw tokens.

Tokens retain their exact source spans and lexical bytes. Token classes are integer, real, Hollerith string, Directory Entry pointer, omitted value, parameter delimiter, record delimiter, and retained uninterpreted value. An empty or blank-only Parameter Data field is an omitted value. A required-default integer or real field uses its defined explicit default or the data-type default zero. A logical field defaults to false. A string field defaults to the null string. A pointer field defaults to zero only when its entity field defines zero or default semantics. Count fields and non-null constituent pointers are required-no-default fields. A supplied token must have the field's lexical type; a wrong-typed token does not select a default. A record delimiter supplies every remaining trailing required-default field. Entity accessors impose field-specific token types and arity. Pointer interpretation is field-specific; a numeric token is not globally coerced to a pointer. These are the field-category and free-format rules in [IGES 5.3 §§2.2.1–2.2.3](https://paulbourke.net/dataformats/iges/IGES.pdf).

Semantic output writes every finite nonzero real directly with 17 significant decimal digits and a `D` exponent, declares 17 double-precision significant digits in Global field 11, and writes either sign of zero as `0`. It does not apply a comparison tolerance or lower-precision pre-rounding during serialization. This CADIR writer profile round-trips every finite binary64 value without flushing small nonzero values to zero. Generated Parameter Data cards end immediately after a parameter or record delimiter when the next field fits; a generated numeric field or Hollerith header longer than the 64-byte Parameter Data area is refused, while a counted Hollerith payload may cross cards. On input, card boundaries constrain lexical validity: only a Hollerith payload may cross, and its count and `H` header must stay on the first card; a numeric field and its delimiter must stay on one card. Delimiter-aligned output is an interoperability convention.

A semantic edge parameter range has a finite start strictly less than its end. A zero-length range is a degenerate edge and is refused; it is never promoted to a revolution. An unreferenced circle or ellipse uses one complete revolution. A referenced circular or elliptical edge whose model-space start and end points are identical is also complete. Generated complete Type 100 and Type 104 arcs copy the two start-coordinate tokens to the terminate coordinates byte for byte.

A declared count applies only when the record holds the items it counts before the end of the entity-specific parameters. The entity layouts that establish these widths are defined by [IGES 5.3 §§4.6–4.7, 4.14–4.16, 4.46, 4.58–4.62, 4.64, 4.67–4.70, 4.73, 4.77–4.79, 4.80–4.96, 4.97–4.107, 4.123, 4.126, 4.136–4.137, and 4.141](https://paulbourke.net/dataformats/iges/IGES.pdf); the entity-specific boundary precedes the trailing pointer groups defined by [§2.2.4.5.2](https://paulbourke.net/dataformats/iges/IGES.pdf). A counted fixed-width list whose entity-specific boundary is below the record end does not reach the record delimiter, so the delimiter defaults no field of it: every one of its items is complete and its declared count requires `count * width` tokens. A counted fixed-width list that runs to the record end holds its final item in whole or in part, because the record delimiter supplies the explicit or implicit default of every remaining field under [§2.2.3](https://paulbourke.net/dataformats/iges/IGES.pdf). Such a list holds `ceil(A / width)` items, where `A` is the token count between the count field and the entity-specific boundary. A declared count up to that number is the count the record holds; the omitted fields of a partly present final item take their defaults and no omitted field crosses the entity-specific boundary. A declared count above that number is a count the record does not hold: the list is not read, and the decoder charges `iges/parameter.count-overdeclared` once on the owning Directory Entry. That code reports under `NoncanonicalSourceSyntax` at Warning severity on the same ground as the record quarantines: a count the record does not hold is a defect in the source syntax, not an entity this codec does not read, and it removes one list while the rest of the document stays usable. This loss is reported in both container-only and full decodes. A full strict decode therefore refuses such a file, and a salvage decode keeps the declared count in the native record with an empty item list. The General Note string list of [§4.60](https://paulbourke.net/dataformats/iges/IGES.pdf) and the New General Note string list of [§4.61](https://paulbourke.net/dataformats/iges/IGES.pdf) are the last entity-specific parameters of their records and take this rule. If a nested counted sequence is incomplete, its declared count remains present, its typed item list is empty, and no later token is reinterpreted as the start of a sibling item. Every counted native record retains its declared count separately from its typed items. Type 402 Forms 9, 13, 16, 18, 20, and 21 retain their child, geometry, entity, flow, connection, join, name, name-display, and continuation counts as applicable. The decoder applies this rule at the selected entity-specific boundary. Every semantic projector uses the boundary where the record's trailing pointer groups begin for fixed fields and counted lists; trailing pointer groups remain relationship data and are not entity fields. Semantic projection requires a counted list to reach that boundary, and it refuses a record whose declared list stops short of it. The native reader reads the same list at the entity-specific boundary. A record that holds surplus tokens after its complete declared list therefore retains those items in the native record while its semantic projection is refused. This is a CADIR recovery decision: if an item in a native outer list or a nested counted sequence is incomplete, that projected list is empty; raw Parameter Data tokens remain in the native entity record, and later sibling fields are read only after preceding variable-width lists are complete.

Type 406 Form 11 puts `NP`, `PTYPE`, `ND`, and `NI` at Parameter Data indexes 1 through 4 under [IGES 5.3 §4.107](https://paulbourke.net/dataformats/iges/IGES.pdf). `TYPI(1..NI)` occupies indexes `5..4+NI`; `NVALI(1..NI)` occupies indexes `5+NI..4+2*NI`; the `VALI` lists follow in independent-variable order; and the `VALD` list follows the complete `VALI` span. Let `S = sum(NVALI(i))` and `P = product(NVALI(i))`, with the empty product equal to one when `NI = 0`. The `VALD` list contains `ND*P` values, the first trailing pointer-group count is token `5 + 2*NI + S + ND*P` after the entity type token, and `NP = 3 + 2*NI + S + ND*P`. `ND` is positive, `NI` is nonnegative, and every `NVALI(i)` is positive for a CADIR-admitted table. The `NI = 0` form has no independent-variable type, count, or value list and contains `ND` dependent values.

The decoder selects that boundary only when the complete nested span fits, its arithmetic does not overflow, and `NP` matches the formula. A malformed count, a truncated list, an overflowing count, or an `NP` mismatch has no usable entity-table boundary and does not enable generic suffix recovery. A wrong-typed `VALI` or `VALD` value does not change a complete count-defined boundary; its native value slot is null and semantic property projection rejects the property. If a nested count is malformed or its list is incomplete, all typed lists are empty; the declared counts and raw Parameter Data tokens remain in the native property and no later token becomes a typed sibling value. This is the CADIR recovery rule for an incomplete counted property.

Type 406 Form 1 stores positive `NP` followed by `NP` level identifiers at Parameter Data indexes 2 through `1+NP` under [IGES 5.3 §4.98](https://paulbourke.net/dataformats/iges/IGES.pdf). The first trailing pointer-group count is token `2+NP`. The native definition-level projection applies the selected entity-specific boundary: a complete span retains that boundary when a level has the wrong lexical or value domain, while a missing, nonpositive, wrong-typed, or incomplete count/list retains no typed levels and suppresses generic trailing-pointer recovery. A valid Definition Levels property has distinct nonnegative level numbers; a negative Directory Level points to its odd Directory Entry sequence.

The V5.0 read profile applies the null-string rule to a one-string General Note: a one-blank Hollerith text value (`1H `) and a defaulted final text field both represent null text, while the declared character count remains source data. The raw Parameter Data record retains the original representation. This postprocessor rule is [IGES 5.0 Recommended Practices Guide RP 45](https://nvlpubs.nist.gov/nistpubs/Legacy/IR/nistir4600.pdf).

## Record quarantine

A defect inside one record does not refuse the file. The decoder separates three tiers of defect. A framing defect that leaves record boundaries or the section census unknown refuses the file. A defect attributable to one Directory Entry record, or to one entity's Parameter Data, quarantines that record: the decoder retains its raw card bytes under a stable identity, accounts for it in the transfer ledger, and charges a loss. An integrity or resource failure refuses the request unchanged. This section is the contract for that separation. It states what the decoder produces for each defect class, and it holds for both container-only and full decodes.

### Card framing and the boundary-recovery reading

[IGES 5.3 §2.2](https://paulbourke.net/dataformats/iges/IGES.pdf) defines the Fixed ASCII file as an ordered sequence of 80-column card images. A line terminator is a media convention that separates card images; it is not part of the data model. Two facts place a card. The section marker in column 73 names the section that owns it, and its position fixes its order inside that section. The marker is not recoverable from position, because a section boundary is exactly where the markers change. The sequence is recoverable from position, because §2.2 defines the sequence as the position. A card-scan defect therefore refuses the file when the marker is unreadable or contradicts the canonical section order, and is recovered when the defect lies in a declaration that the card census already fixes.

| Card-scan defect                                                                                                           | What the file still fixes                                                               | Disposition                                                                                                                                                                                                                                                                                                                                                                                      |

This table states what the card scan produces, and the card scan runs only after representation classification admits the file. Classification reads exactly two card images from the first 512 bytes: the first card image of the first line, and the second card image of that line when the line divides into cards, or the first card image of the next line when it does not. It requires both to be complete 80-byte cards, the first to carry the `S` marker with sequence `1`, and the second to carry `S` with sequence `2` or `G` with sequence `1`. It requires columns 74 through 80 of both cards to hold a right-aligned decimal sequence, padded with blanks or zeroes, whose value is greater than zero. A blank, left-aligned, or non-digit sequence field in either of those two cards is a wrong-format refusal, and the file never reaches the positional-sequence recovery in this table. Classification is stricter than the scan on purpose: it is the format-identity gate, it has only the prefix to decide on, and the two section markers alone are two bytes of evidence. Bytes before the first card image are not a card image, so a leading blank line, a byte-order mark, or any other preamble is a wrong-format refusal for the same reason. A stream with no line terminator in its prefix is classified from the same two card images under the first row of this table.

Recovered sequences are authoritative for identity. Every Directory Entry identity, every Directory Entry pointer target, and every Parameter Data back-pointer resolves against positional sequences, so one misnumbered card changes only its own identity.

The post-Terminate rule is dialect-specific. Type 5.x retains unsequenced physical lines after the Terminate card as source records and ignores them for section parsing. IGES 4.0 requires the Terminate Section to be the last physical line; a V4.0 read retains any later records and reports `iges/global.noncanonical-framing`. The retained bytes remain available through the native card arena and source fidelity.

### Quarantined records

Every Directory Entry is either typed or quarantined. A consumer of a typed Directory Entry sees only fields read from the file, never a substituted one. A field the parser could not read has no interpretation, so a quarantined record carries none. A quarantined record is retained under a stable identity that the transfer ledger and the reference graph name.

One quarantine record covers one whole Directory Entry, which is the two-card pair. A defect in either card quarantines the pair. A Directory Entry section with an odd card count quarantines its trailing unpaired card as one record; pairing is anchored at sequence one, so the unpaired card is the last one.

Quarantined records count as native entities for resource accounting, on the same charge as every other native record.

Every quarantined record is accounted in the transfer ledger as retained. The ledger omits a null entity only when the file states entity type `0`; a quarantined record states nothing, so it is accounted rather than assumed null. Ledger verification stays fatal, and a failure there is a decoder defect and not a source defect.

### Pointers into a quarantined record

A Directory Entry pointer or a Parameter Data pointer whose target sequence names a quarantined record has dangling resolution and charges `iges/graph.pointer-unresolved`. The graph indexes the typed list, so a quarantined sequence is absent from the index and the existing dangling path applies. The loss code does not distinguish an absent record from a quarantined one; the quarantine loss names the same sequence.

### Pointers out of a quarantined record

The decoder does not analyze the outbound pointers of a quarantined Directory Entry record. Its structure, line-font, level, view, transformation, label-display, and color pointers are the same eight-byte fields that failed typing. Reading a pointer out of a field that is not known to hold a signed decimal integer would report a reference the file does not state, which is fabrication, not recovery. A quarantined record therefore contributes no edge to the reference graph and charges no pointer loss of its own. Its raw bytes retain every pointer field for a consumer that chooses to inspect them.

### Parameter Data quarantine

A defect in one entity's Parameter Data quarantines that entity's parameter data and nothing else.

- The typed Directory Entry stays in the typed list with all twenty fields.
- The entity is not projected to neutral IR. No geometry, annotation, or product record is derived from tokens that were not read.
- The raw Parameter Data text is retained under the quarantine identity. It has no other typed home.
- The decoder charges one `iges/parameter.data-quarantined` loss whose provenance tag is `D<sequence>:parameter`. The reader counts that as an attributed loss, so the generic `iges/entity.retained-unprojected` note is not also charged and the entity's ledger note states that projection was omitted with an attributed loss.

Ownership of Parameter Data cards resolves in a fixed order, because the Directory Entry declaration and the card back-pointers are redundant statements of the same fact and either can be the broken one.

1. The declared range applies when the Directory Entry Parameter Data start and line count are positive values inside the unsigned 32-bit range and every Parameter Data position in `start` through `start + count - 1` exists. The range is primary because [§2.2.4.5](https://paulbourke.net/dataformats/iges/IGES.pdf) makes the Directory Entry the index of its parameter data and columns 65 through 72 a back reference to it.
2. Otherwise the back-pointer census applies: the contiguous run of Parameter Data cards whose back-pointer names this entry.
3. Otherwise the entity's Parameter Data is quarantined.

Throughout these rules, an existing entry is one in the typed list. A back-pointer that is absent, unreadable, zero, even, or names no existing entry does not quarantine anything when rule 1 claims the card; the disagreement charges `iges/card.framing-recovered`. Any use of rule 2, and any disagreement between rule 1 and the back-pointer census, charges the same code. A readable back-pointer that names a different existing entry is a conflict rather than a broken declaration: it quarantines the Parameter Data of both entries, as does a card that two declared ranges claim. A Parameter Data card that no entry claims under either rule, and whose back-pointer names no quarantined Directory Entry record either, is retained in the `cards` arena, belongs to no record, needs no quarantine record and no ledger row, and charges `iges/card.framing-recovered`.

A quarantined Directory Entry record owns no Parameter Data. Its declared range is not typed, so rule 1 cannot run for it, and the cards whose back-pointer names its sequence are unclaimed cards: the `cards` arena retains them, they get no quarantine record and no ledger row of their own, and they charge no framing loss. The record's own `iges/directory.record-quarantined` loss covers them, and the quarantine identity space holds one record per broken source record rather than two.

A non-null entity that declares zero Parameter Data cards has no declared range, so rule 2 decides: when a Parameter Data card's back-pointer names it, that contiguous run is its parameter data and the disagreement charges the framing loss; when no card names it, its quarantine record holds zero cards and no bytes. The zero-card record exists so that the entity's missing parameter data has one identity and one ledger row, on the same terms as every other quarantined record. A record with no card takes the byte offset of its owning Directory Entry's first card, because it has no first card of its own.

### Loss codes

Three codes cover both quarantine classes and every recovered framing defect. Each names one consequence class, which is what a report consumer acts on.

| ----------------------------------- | -------------------------- | -------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `iges/directory.record-quarantined` | `NoncanonicalSourceSyntax` | Warning  | Rejected. The taxonomy floor is Warning. | One Directory Entry record whose typed fields were not recovered: a non-ASCII field, a field that is not a decimal integer, an invalid status number, a repeated entity type that disagrees, or an unpaired card                                                                                            |

All three use `NoncanonicalSourceSyntax` rather than `RecordNotTyped`. `RecordNotTyped` states that this codec does not type a record, which is a claim about the read envelope; a quarantine states that the file does not hold the record it declares, which is a claim about source syntax. The strict consequence follows the same split. A strict caller accepts that the reader does not cover an entity type, and its taxonomy declares no floor; a strict caller must not silently accept a file whose Directory Entry is not a Directory Entry, and `NoncanonicalSourceSyntax` floors at Warning. Severity is Warning, not Blocking, because a quarantined record removes one record and leaves the rest of the document usable, which is the same weight as `iges/global.noncanonical-framing`.

Each message names its record and its defect.

A file that misnumbers every card charges one note, not one note per card: `iges/card.framing-recovered` is charged at most once for each pair of section and defect class, where the defect classes are a recovered card boundary, a recovered sequence, a recovered Parameter Data owner, an unclaimed Parameter Data card, and a replaced Terminate count. The two quarantine codes are charged once per quarantined record.

## Entity graph

The entity identity is its odd Directory Entry sequence. Graph construction indexes all identities before resolving references. Each pointer evaluation has resolved, null, dangling, out-of-range, even-sequence, wrong-type, or cyclic resolution. A zero pointer has null resolution and creates no edge because it specifies no relationship; the raw zero remains in the native Directory Entry record. Each edge records the source entity, source field or parameter index, raw pointer, expected target class, and non-null resolution state. A value that cannot identify a Directory Entry because its sign or magnitude is invalid has out-of-range resolution. Each unresolved edge is a `reference_graph_not_closed` loss with the source Directory Entry identity and byte offset. Transformation links compose recursively and a transformation cycle has cyclic resolution. The other Directory Entry links select definitions or display entities and do not compose into same-kind reference chains.

Parameter Data pointer sign interpretation is field-specific. A positive pointer uses its value as the Directory Entry sequence. A field that defines a negative pointer encoding uses the negated magnitude and retains the signed raw value. A nonzero candidate resolves only if its sequence fits `u32`, is odd, identifies an existing Directory Entry, and satisfies the field's entity-type, form, and Directory-status target class. Only a resolved parameter pointer creates a typed arena identity. An unresolved parameter pointer leaves the typed arena field null and remains a reference edge. Its loss offset identifies the first byte of the source parameter token.

An entity retains its type, form, Directory Entry fields, status fields, ordered parameter tokens, trailing association and property groups, source spans, and reference edges. Unsupported type/form pairs remain named native records and prevent any support claim whose closed envelope admits the pair.

## Units and transformations

Model-space lengths equal native values divided by the Global model-space scale and converted from the declared unit to millimetres. Dimensionless values, parameter coordinates, weights, and unit direction vectors are not length-scaled. Angles convert to radians when projected to neutral IR. A transformation matrix is a 3-by-3 linear part plus translation. Translation is length-valued. Entity transforms compose from the entity definition toward model space exactly once. Definition, subfigure-instance, and occurrence transforms remain separate native relationships.

A candidate suffix is structurally closed when its nonnegative counts consume the complete remaining token sequence and at least one pointer is present. A candidate is target-valid when every association pointer is odd and names Type 402, Type 212, or Type 312, and every property pointer is odd and names Type 316, Type 322, Type 406, or Type 422. When the entity table supplies `NV`, the suffix at `NV + 1` is the only boundary considered. Otherwise, the typed suffix is the unique target-valid candidate under the CADIR generic recovery rule. Its start is the primary-parameter end, its pointers are parameter-reference graph edges, and the native entity's `association_links` and `property_links` preserve resolved group membership and pointer order independently from Directory references. If no candidate is target-valid, or if more than one generic candidate is target-valid, the decoder does not infer a boundary: it retains the complete token sequence as primary parameters and creates no association or property links. In the multiple-valid case it emits one `parameter.boundary-ambiguous` loss with the owning Directory provenance before native projection.

Type 402 Forms 1 and 14 provide independent evidence that each listed member has a trailing associativity group. For a listed member, more than one structural candidate with no target-valid candidate also emits `parameter.boundary-ambiguous`; a single structurally closed target-invalid candidate remains untyped for pointer diagnostics. Each candidate pointer is classified in the reference graph. An unresolved candidate produces `reference_graph_not_closed` at its exact parameter-token offset. Candidate pointers do not create `association_links` or `property_links`. Arithmetic closure without this reverse relationship does not establish a malformed suffix because ordinary entity parameters can have the same counted shape. The complete original token sequence remains in `parameters`.

## Topology

Manifold solid B-rep entities preserve source vertex, edge, loop, face, shell, and solid identity. Edge uses reference shared edge identity; loop orientation and face same-sense fields determine coedge and face orientation. A solid region's ordered shell list is the neutral role contract: the decoder stores the Type 186 `SHELL` pointer first and the void-shell pointers afterward in source order, and the writer emits that order. Type 186 writes the first shell as `SHELL` and the remaining shells as its ordered void list. The writer does not infer or replace these roles from geometric containment.

Every use of one Edge List item in a shell belongs to one cyclic radial ring. A closed Form 1 shell requires exactly two opposite-sense uses per edge. An open Form 2 shell preserves one, two, or more uses without imposing the closed-manifold cardinality rule; rings with more than two uses represent explicit non-manifold sharing.

A Form 1 Edge List Entity (Type 504) stores a positive ordered list of model-space curve pointers and one-based start and end indices into Form 1 Vertex List entities. Evaluating the curve at its stored parameter interval endpoints must agree with the referenced vertex points within the Global minimum resolution. An inconsistent edge prevents attachment of every topology candidate that consumes it. The edge-list order is not an ownership signal.

A Form 1 Loop Entity (Type 508) stores a positive ordered use count. Each use selects an Edge List or Vertex List item, stores an orientation logical, and stores an arbitrary ordered sequence of `(ISOP, CURV)` parameter-curve pairs. Each `ISOP` field is a required logical: true declares that its parameter-space curve is isoparametric on the face surface, and false declares that it is not. These meanings and the field layout are defined by [IGES 5.3 §4.145](https://paulbourke.net/dataformats/iges/IGES.pdf). Edge uses become coedges. Vertex uses become pole uses positioned after the preceding edge use in cyclic loop order, or the sole unanchored use of a vertex-only loop. Every parameter curve remains ordered and retains its isoparametric logical. The parameter-curve collection forms one connected parameter-space image. Composing its first endpoint, adjacent joins, and final endpoint with the face surface must agree with the oriented edge vertices within the Global minimum resolution. A pole-use collection has the same endpoint contract with the pole vertex. Disagreement prevents attachment of the containing topology candidate.

The Type 502, 504, 508, 510, and 514 primary Parameter Data spans place trailing pointer groups after the complete topology table under [IGES 5.3 §§4.143–4.147](https://paulbourke.net/dataformats/iges/IGES.pdf). Type 502 Form 1 starts groups at token `2 + 3*N`; Type 504 Form 1 starts them at `2 + 5*N`; Type 510 Form 1 starts them at `4 + N`; and Type 514 Forms 1 and 2 start them at `2 + 2*N`. Type 508 Form 1 starts at token 2 and advances by `5 + 2*K` for each edge use, where `K` is that use's parameter-curve count. All listed counts are positive except `K`, which may be zero. `parameter.rs::entity_primary_end` applies checked spans for these forms. A missing, nonpositive, wrong-typed, overflowing, or physically incomplete count or nested span leaves the raw Parameter Data without a usable table boundary and suppresses generic trailing-pointer recovery.

For CADIR B-rep projection, a Type 508 edge use may obtain its neutral source Edge range only from exactly one source occurrence whose curve identity matches the Type 504 carrier and whose retained parameter-interval endpoints agree with the Type 504 start and terminate vertices within the Global minimum resolution. Zero matches or multiple matches refuse the topology candidate. The decoder does not select a source occurrence by Edge List order. The Type 504 carrier and the Type 508 use semantics are defined by [IGES 5.3 §§4.144–4.145](https://paulbourke.net/dataformats/iges/IGES.pdf).

A Form 0 Bounded Surface Entity (Type 143) has one `TYPE` representation value for all of its Boundary Entities. `TYPE=0` requires every Boundary Entity to contain model-space curves only; `TYPE=1` requires every Boundary Entity to contain model-space curves and associated parameter-space curve collections. These requirements are defined by [IGES 5.3 §§4.31 and 4.33](https://paulbourke.net/dataformats/iges/IGES.pdf). Semantic output rejects an unclassified face whose boundary loops do not all have the same parameter-curve presence; it does not select the value from loop order or alter a loop's representation.

A Form 1 Face Entity (Type 510) stores a support-surface pointer, a positive loop count, an outer-loop logical, and the ordered loop pointers. When the logical is true, the first loop is the sender-selected outer loop and the remaining loops are the other bounds. When it is false, no outer loop is identified. The semantic writer emits the logical only from an explicit `outer` role, refuses a mixture of classified and unclassified B-rep loops, and emits false for an entirely unclassified face. The decoder maps a false logical to `Unspecified`; it does not invent an inner role. A cylindrical face boundary loop that repeats one seam edge without an axial boundary does not delimit a finite region and is refused by the semantic writer.

Boundary and curve-on-surface entities are valid independent entities and do not require a bounded-surface or trimmed-surface owner. When a bounded-surface or trimmed-surface entity consumes them, they carry face-local boundaries and produce sheet regions whose loops, coedges, edges, and vertices are owned by the source face. No cross-face edge sharing is inferred without a shared source topology entity. A topology candidate is attached only after the complete neutral ownership and reference graph validates. A failed topology candidate records a loss only on its owning bounded-surface or trimmed-surface entity.

Face-local carrier agreement uses the Global minimum resolution in model units. Boundary-ring closure uses a topology sewing tolerance equal to the larger of the Global minimum resolution and one coordinate quantum at the largest absolute endpoint coordinate, where the quantum follows the Global single-precision significant-digit count. Boundary endpoints use the transitive closure of that tolerance relation. A connected component whose diameter exceeds the tolerance is non-transitive and invalid; it does not select a representative by source order. A valid component uses its lexicographically smallest endpoint as its representative. Local vertex identities follow first endpoint order and are names only; they do not select the topology cluster. The resulting vertices, edges, and face store that sewing tolerance. Exact conversion of a source parameter curve to neutral NURBS geometry has no fit tolerance; the Global resolution is not recorded as an approximation bound.

Declared surface parameter domains remain attached to the exact procedural surface construction. Type 118 retains the active first-rail interval and the interpolation interval `[0, 1]`. Its direction flag reverses the second rail without changing the surface parameter domain. Its developability flag is retained in the native entity's ordered parameter tokens but is not represented by the neutral ruled-surface carrier; a successful Type 118 projection emits `geometry.ruled-developability-not-transferred` with source provenance. Type 120 retains the generatrix interval and `[SA, TA]`. Type 122 retains the directrix interval and `[0, 1]`. Type 128 retains its increasing `[U(0), U(1)]` and `[V(0), V(1)]` subranges both as ordered exact-surface parameters and as record bounds. A Type 128 bound outside its active knot domain by no more than its declared real representation uncertainty is clamped to the domain endpoint. A larger disagreement, an empty interval, or a permutation of the four range fields is invalid. A periodic parameter may use one unwrapped period at a seam; the equivalent interval remains within the declared periodic domain.

Type 140 evaluates the oriented unit normal of its support at `(Um, Vm)` under [IGES 5.3 §4.30](https://paulbourke.net/dataformats/iges/IGES.pdf). A bounded support uses `Um = (U0 + U1) / 2` and `Vm = (V0 + V1) / 2`; an unbounded support uses `(0, 0)`. The declared offset indicator must agree, within its real representation uncertainty, with that normal or its negation. Agreement selects positive support-normal distance; negation selects negative support-normal distance. An arbitrary unit vector is not an offset indicator. The indicator selects the sign only and does not replace the varying normal field used to evaluate the offset.

Type 140 Form 0 stores `NX`, `NY`, `NZ`, `D`, and `DE` at Parameter indexes 1 through 5 under [IGES 4.0 §3.23](https://www.govinfo.gov/content/pkg/GOVPUB-C13-7b81ba8b0f709555f162cb496aa63b3b/pdf/GOVPUB-C13-7b81ba8b0f709555f162cb496aa63b3b.pdf) and [IGES 5.3 §4.30](https://paulbourke.net/dataformats/iges/IGES.pdf). The first trailing pointer-group count is token 6. `parameter.rs::entity_primary_end` applies this fixed table boundary when all five primary fields are physically present; an incomplete primary span or incomplete token-6 group is retained without generic suffix recovery.

A Form 0 Boundary Entity (Type 141) stores `TYPE`, `PREF`, the support-surface pointer, and a positive model-curve count. Each ordered model-curve item stores its curve pointer, sense (`1` forward or `2` reversed), pcurve count, and that many parameter-curve pointers. `TYPE=0` requires every pcurve count to be zero. `TYPE=1` requires every pcurve count to be positive. The parameter curves of one item remain ordered and together form that coedge's parameter-space image. These `TYPE` meanings are defined by [IGES 5.3 §4.31](https://paulbourke.net/dataformats/iges/IGES.pdf).

For Type 141, item `i` starts at Parameter index `5 + 3*(i - 1) + K(1) + ... + K(i - 1)`. Its three fields are `CRVPT(i)`, `SENSE(i)`, and `K(i)`, followed by `K(i)` `PSCPT(i,j)` pointers. The last specified primary index is `4 + 3*N + K(1) + ... + K(N)`, so trailing pointer groups begin at token index `5 + 3*N + K(1) + ... + K(N)` after the entity type token. `N` is positive; every `K(i)` is nonnegative, and `TYPE=0` requires `K(i)=0` for every item. A missing, nonpositive, negative, or overflowing count has no usable entity-table boundary.

Type 141 `PREF=1` selects the model-space trimming curves for neutral topology. Values `0`, `2`, and `3` select the parameter-space collections when present and require their composed endpoints to agree with the model-space curves. The four Type 141 preference meanings are defined by [IGES 5.3 §4.31](https://paulbourke.net/dataformats/iges/IGES.pdf). The associated parameter-space curves must remain inside each finite declared support bound over their active ranges. An out-of-domain alternate is omitted when the model-space curve is preferred and invalidates the topology candidate when parameter curves are authoritative. Type 142 reverses the numeric preference roles: `PREF=1` selects the composed parameter-space curve, `PREF=2` selects the model-space curve, and values `0` and `3` use both equally. These preference meanings are defined by [IGES 5.3 §4.32](https://paulbourke.net/dataformats/iges/IGES.pdf). An agreeing alternate parameter-space representation remains attached to the neutral coedge even when the model-space curve is preferred. A disagreeing or undecodable alternate is omitted when the model-space curve is preferred. A selected parameter-space representation that disagrees beyond the Global minimum resolution invalidates the topology candidate.

A Form 0 Curve on a Parametric Surface Entity (Type 142) stores its creation method, support-surface pointer, parameter-space curve pointer, model-space curve pointer, and preferred representation. The parameter-space curve has entity-use flag `05`. Its composition with the support surface has the same oriented model-space endpoints as the model-space curve. Projection requires every active parameter-space point to lie inside each finite declared support bound and both endpoint distances to be no greater than the Global minimum resolution. Positive-weight NURBS pcurves prove the bound by their active-range rational control hull. A parameter-preferred boundary outside a declared bound is rejected. A model-preferred boundary retains the model-space curve, omits the alternate pcurve, and records a loss. A support without retained finite bounds uses endpoint agreement only. The creation-method and preference fields are defined by [IGES 5.3 §4.32](https://paulbourke.net/dataformats/iges/IGES.pdf).

Type 142 Form 0 has five primary Parameter Data fields at indexes 1 through 5: `CRTN`, `SPTR`, `BPTR`, `CPTR`, and `PREF`. `CRTN` is `0` for unspecified, `1` for projection, `2` for intersection, and `3` for an isoparametric curve. `SPTR` points to the support surface. `BPTR` points to the entity that contains the parameter-space curve `B`; `CPTR` points to the model-space curve `C`. `PREF` is `0` for unspecified, `1` for the composition `S o B`, `2` for `C`, and `3` when both representations are equally preferred. Additional pointer groups begin at token index 6 after the entity-type token. A complete five-field span keeps this boundary even when a primary token has the wrong lexical type or value. (CADIR decision) Fewer than five physical primary tokens, or an incomplete group beginning at token 6, retains the raw Parameter Data and suppresses generic trailing-pointer recovery.

Type 141 and Type 142 model-curve pointers identify curve carriers, not Type 504 edge occurrences. Projection validates each candidate occurrence by evaluating its retained parameter interval against its start and terminate vertices. A parameter-curve collection selects a candidate only when its oriented composed endpoints agree with exactly one validated occurrence. A model-preferred item without an agreeing parameter collection selects only one validated occurrence; no collection or multiple validated occurrences do not select by edge-list order and refuse the topology candidate.

Semantic Type 141 output sets `TYPE=0` when its model-space boundary has no parameter curves and `TYPE=1` when every coedge has a parameter-curve collection; the writer refuses a mixed loop. It sets `PREF=1` because the neutral edge carrier is the authoritative trimming curve. Semantic Type 142 output sets creation method `0` because neutral IR does not identify projection, intersection, or isoparametric provenance, and sets `PREF=2` because the model-space edge carrier is authoritative while the parameter curve is accepted within the declared topology tolerance. These selected values are the IGES values defined in [IGES 5.3 §§4.31–4.32](https://paulbourke.net/dataformats/iges/IGES.pdf). The semantic Type 508 writer emits the required `ISOP` logical from explicit neutral `PcurveUse.isoparametric = Some(false)` or `Some(true)`. It refuses `None` because the missing source declaration is not false or true. The generated status values follow the four fields in [IGES 5.3 §2.2.4.4.9](https://paulbourke.net/dataformats/iges/IGES.pdf): Type 141, Type 142, Type 502, Type 508, Type 510, and Type 514 Form 1 constituent records use `00010000` (physically dependent, entity-use `00`, hierarchy `00`); Type 504 uses `00010001` (physically dependent, entity-use `00`, hierarchy `01`), as required by [IGES 5.3 §4.144.1](https://paulbourke.net/dataformats/iges/IGES.pdf), so its subordinate records retain their own display attributes; and independent geometry, Type 514 Form 2, and Type 186 use `00000000` (independent, entity-use `00`, hierarchy `00`). Type 514 Form 1 is physically dependent on its parent under [IGES 5.3 §4.147](https://paulbourke.net/dataformats/iges/IGES.pdf). Parameter-space curve entities use `00010500` (physically dependent, entity-use `05`, hierarchy `00`).

The semantic export census names every emitted standard entity type, including each physically dependent Direction Entity as `123_direction`. `unknown_entity` counts only an emitted type with no standard census mapping.

A Form 0 Trimmed Surface Entity (Type 144) stores a support-surface pointer, an outer-boundary flag, an inner-boundary count, an outer Curve on a Parametric Surface pointer, and the ordered inner Curve on a Parametric Surface pointers. When the outer-boundary flag is zero, the outer pointer is zero or omitted and the rectangular parameter domain of the support surface supplies the outer boundary. The entity then produces no explicit outer loop; each listed loop is `inner`. When the flag is one, the outer pointer is present and produces the single `outer` loop; each listed loop is `inner`.

## Appearance

Directory color zero supplies no direct color. Positive values `1` through `8` select black, red, green, blue, yellow, magenta, cyan, and white. A negative value is the negated odd Directory sequence of a Form 0 Color Definition Entity (Type 314). These standard color meanings are defined by [IGES 5.3 §2.2.4.4.13](https://paulbourke.net/dataformats/iges/IGES.pdf). Type 314 stores red, green, and blue intensities as finite percentages from `0` through `100` and an optional Hollerith name under [§4.76](https://paulbourke.net/dataformats/iges/IGES.pdf). Neutral RGBA components equal the percentages divided by `100`, with alpha `1`.

Directory line-font values `1` through `5` select standard patterns, while `0` means no pattern. A negative value is the negated odd Directory sequence of a Line Font Definition Entity (Type 304). The standard table is defined by [IGES 5.3 §2.2.4.4.4](https://paulbourke.net/dataformats/iges/IGES.pdf). Form 1 stores an orientation flag `0` or `1`, a Form 0 Subfigure Definition pointer, a positive display spacing, and a positive template scale. Form 2 stores a positive segment count, that many positive segment lengths, and exactly `ceil(count / 4)` hexadecimal digits. Pattern bits are right-justified; the unit bit describes the last segment, and unused high bits are zero. Type 304 has entity-use flag `02` and carries a standard fallback line-font value `1` through `5` in its Directory entry under [IGES 5.3 §4.70](https://paulbourke.net/dataformats/iges/IGES.pdf).

A nonnegative Directory level value selects that single exchange-file level. A negative value is the negated odd Directory sequence of a Definition Levels Property Entity (Type 406, Form 1). The property stores a positive count followed by that many distinct nonnegative level numbers. A malformed definition or link is retained but does not become a decoded display-level set.

The CADIR `display_attributes` arena preserves every signed Directory display number. It exposes a typed definition identity only when the reference graph resolves the negative pointer to an existing target admitted by the corresponding native arena: Type 304 Form 1 or 2 for a line font, Type 406 Form 1 for a definition level, or Type 314 Form 0 for a color. A missing, even-sequence, out-of-range, or wrong-type/form target leaves the typed field null and retains the signed number. The graph records one attributed `graph.pointer-unresolved` loss on the source Directory Entry. This is a CADIR projection decision; it does not replace an invalid pointer with a display default. These values remain distinct from effective neutral appearance bindings.

A positive Directory line-weight number selects that numbered increment in the uniform Global line-weight series and cannot exceed the Global maximum gradation count. With a positive Global field 17, its model-space width is `number * maximum_width / maximum_gradations`; neutral/native display width converts that result to millimetres. With V5.0 Global field 17 equal to zero, the same bounded number is relative: it requests that many standard strokes and has no physical width in the CADIR display record. Zero leaves the display width unspecified.

A Manifold Solid B-rep Object or orphan Shell color binds to its body. A Face color binds to that face and overrides the body color for that face. Trimmed and bounded surface colors bind to their generated sheet body and face. The blank-status field determines body visibility. Curve and surface source-object associations retain their direct Directory colors.

## Byte accounting

The Fixed ASCII reader retains every physical card and every Directory/Parameter entity in `native.iges`, including typed domain arenas where projected and generic entity records otherwise. Card payloads, line endings, Directory fields, Parameter tokens, links, and source identities remain available through that namespace. `SourceFidelity` retains the complete source image as a byte record and records its document-local SHA-256 digest. The reader emits a closed `transfer_ledger` for every non-null Directory entity and for every quarantined record, and verifies it against the decoded model.

## Decode admission

A successful semantic decode has no error-severity neutral-validation finding.
The reader validates referential integrity, geometry domains, topology
ownership, endpoint agreement, pcurve agreement, transforms, and document
invariants before it returns the document. A failed candidate does not commit
partial topology.

Every non-null Directory Entry has one retained native identity and one
`transfer_ledger` disposition, and so does every quarantined record. A
supported entity without neutral projection has a stable namespaced loss code,
source provenance, and its retained native record. A projected entity with reduced fidelity records the reduction on the
same source identity. Salvage mode records every loss in the decode report.
A full strict decode refuses through the shared decode gate: a loss causes
refusal when its shared taxonomy defines a strict severity floor and the loss
severity reaches that floor. For the current IGES loss set that is exactly
`iges/graph.pointer-unresolved`, `iges/curve.composite-carrier-degraded`,
`iges/source.dialect-unverified`,
`iges/global.semantic-context-substituted`,
`iges/global.length-unit-unresolved`,
`iges/global.noncanonical-framing`,
`iges/directory.record-quarantined`, `iges/parameter.data-quarantined`,
`iges/parameter.count-overdeclared`, and
`iges/card.framing-recovered`. Every other IGES loss is recorded in the
decode report in both modes. A full strict decode therefore refuses a
structurally defective file, and salvage mode recovers it with the losses the
record quarantine section states.

A container inspection has no loss channel, because a container summary carries
notes only. The inspection therefore reports each loss it resolves as one
`loss.<namespace>/<code>=<count>` census note. That census covers the Global
field resolution losses, the dialect loss, the recovered card framing, and both
record quarantines. It does not cover a loss that only a semantic projection
produces, and it does not cover an unresolved pointer, which the inspection
reports through its reference-resolution census instead. A complete loss report
needs a decode.
